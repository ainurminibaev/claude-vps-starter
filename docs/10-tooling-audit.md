# Аудит инструментов Claude и context-mode, 31.10.2026

Проверены фактические Claude JSONL и журнал локального CLIProxyAPI за
30–31 октября 2026 года: 10 недавно изменённых transcript-файлов Mac и
110 transcript-файлов на VPS у 11 пользователей. Записи внутри файлов
фильтровались по timestamp, старые события не включались в результаты.
Это проверка доступных журналов, а не гарантия отсутствия ошибок в несохранённых данных.

## Что сломалось

В Mac-сессии «Айтаб сервис аналитики: пачка ТЗ» обнаружены два результата
инструментов с реальным `rg: command not found`: один shell-скрипт 30 октября
и три скрипта одного `ctx_batch_execute` 31 октября. Повторы одной и той же
ошибки в индексированных выдержках не считались отдельными запусками.

В PATH работающего Claude и его context-mode не было установленного ripgrep.
Копия `rg` внутри Codex 0.166.0 была доступна собственному окружению Codex,
но не subprocess Claude. Ошибка не связана с переводом вызовов в шлюзе.
После каждого сбоя агент выбрал обход: Python 30 октября и JavaScript
31 октября. Следующие чтения исходников и работа над задачей продолжились.

## Измеренная цепочка, московское время

| Эпизод | Ошибка поиска | Результат обхода | Наблюдаемый интервал |
|---|---|---|---:|
| 30.10 | 16:14:17.424 | 16:18:58.816 | 281,392 с |
| 31.10 | 14:43:48.623 | 14:44:08.365 | 19,742 с |

В обоих случаях между ошибкой и результатом обхода записан один новый
ответ основной модели с вызовом `ctx_execute`, затем проверка Auto Mode.
Сумма наблюдаемых интервалов — 301,134 секунды, примерно 5 минут 1 секунда.
Это время цепочек восстановления, не доказанная чистая разница времени всей
задачи относительно запуска с рабочим rg: контрольного повтора исходной задачи нет.

Для 31 октября HTTP-запрос основной модели занял 13,948 с, проверка Auto Mode —
5,827 с. Остальное и небольшое несовпадение суммы со span обусловлены
исполнением инструмента, streaming и разными точками записи timestamps.
Для 30 октября шлюз записал примерно 4 мин 25 с на ответ основной модели и
16,172 с на Auto Mode. Вчерашние минуты прошли в ожидании модели/шлюза,
а не в выполнении Python или медленном поиске на диске. Из этих логов нельзя
разделить очередь upstream, размышления и сетевое ожидание внутри запроса.

Связка request ID: 31 октября `d302772f` — основная модель,
`fa7643b1` — Auto Mode; 30 октября `b2945af9` и `407b7906` соответственно.

## Токены обходных обращений

Usage сгруппирован по уникальному `message.id`. Частичные streaming-записи
одного ответа не суммировались повторно; для каждого счётчика бралось
максимальное зафиксированное значение в этом ответе.

| Обходной ответ | Новый вход | Вход из кеша | Выход | API-эквивалент |
|---|---:|---:|---:|---:|
| 30.10, Python | 295 | 199 552 | 237 | $0,0229152 |
| 31.10, JavaScript | 1 672 | 127 232 | 477 | $0,0208372 |
| Всего | 1 967 | 326 784 | 714 | $0,0437524 |

Это зафиксированный usage двух обращений, вызванных необходимостью обхода,
не точный прирост токенов всей задачи относительно идеального выполнения.
Большой вход — преимущественно чтение уже закешированной истории.
Следующие полезные Read/Edit не записаны в ущерб только из-за того, что
они произошли после сбоя.

API-эквивалент рассчитан для обычного Sol 6.1: $2 за миллион нового входа,
$0,10 за миллион cached input и $10 за миллион выхода. Оба контекста ниже
порога 272K. В native usage output передаётся из Responses `output_tokens`,
а не рассчитывается по длине видимого текста.
[Тариф модели](https://developers.openai.com/api/docs/models/gpt-6.1-sol).

Usage двух проверок Auto Mode в этих transcript-файлах не записан: он
не включён в сумму. Это не списание долларов с подписки и не измеренный
процент её лимита. Цена API и включённый лимит подписки различаются.

## Другие ошибки в проверенных Mac-журналах

Найдены 7 исторических отказов из-за недоступного или просроченного по
времени ожидания classifier `claude-sonnet-5[1m]`, все 30 октября. Это отдельная
проблема доступности служебной модели, а не нехватка rg. Алиас уже добавлен;
последующие живые проверки Auto Mode проходили. Ещё 3 явных отказа
classifier относятся к разрешениям (`Interfere With Workloads`, `Production Reads`)
и не означают поломку плагина. Разрешения не обходились.

Совпадения `async_hooks` оказались строками стека JavaScript в тестах,
а не сбоями lifecycle hooks. Новых `Hook failed`, `unsupported plugin entry type`
или `plugin contents changed` в проверенных tool results не найдено.
Диагностика Codex context-mode 1.0.169 прошла исполнение и FTS5; остаётся
предупреждение определения runtime root через `codex plugin list`.
Дополнительная попытка этой команды за 20 секунд не завершилась; это
предупреждение диагностики регистрации, не воспроизведённая ошибка MCP-вызова.

## Исправление и VPS

На Mac установлен Homebrew ripgrep 15.2.0 в `/opt/homebrew/bin/rg`.
Проверены поиск с PATH уже работающего Claude и реальный RPC `ctx_execute`
той же версии Claude context-mode 1.0.25: команда нашлась и вернула ожидаемое
совпадение. Рабочие сессии не перезапускались.

На VPS системного rg тоже не было. В просмотренных 110 transcript-файлах
за указанный период результатов `rg: command not found` не обнаружено,
поэтому подтверждённый ущерб ботов от этой зависимости не вычислялся.
Установлен только пакет `ripgrep` 14.1.0 из Ubuntu; другие пакеты не обновлялись.
Поиск проверен под всеми 11 пользователями. Все 11 tmux-сессий ботов остались
запущены, gateway service active. Установочные инструкции дополнены зависимостью.

Для восьми общих команд `rg`, `git`, `node`, `npm`, `python3`, `bash`, `jq`, `curl`
после исправления пропусков в проверенных окружениях нет. Это не проверка
всех возможных библиотек, браузеров, проектных зависимостей или задач.

## Почему Auto Mode добавляет секунды

Захвачен запрос настоящего native Claude в отдельной временной сессии.
Первичная проверка запрашивает `thinking: disabled`, `max_tokens: 64`,
`stop_sequences: ["</block>"]`. Её system policy занимает около 141 тысяч
символов; при переводе получается около 30 тысяч входных токенов, большая
часть повторных запросов читается из кеша. Это отдельный сетевой round trip.
Наше общее правило прежде принудительно включало High даже для этих запросов.
В одном повторе зафиксированы 56 reasoning tokens и 4,728 с полного времени.

На момент следующей проверки 31 октября обнаружены 72 завершённые проверки
по алиасу `claude-sonnet-5`, все с HTTP 200; медиана 6,613 с, максимум 43,397 с.
Из этого следует восстановление доступности в этой выборке, но не устранение
всех возможных будущих таймаутов. Официальная документация объясняет,
почему отдельный review добавляет задержку:
[Auto Mode: cost and latency](https://code.claude.com/docs/en/permission-modes#how-auto-mode-evaluates-actions).

В отдельном шлюзе повторён настоящий stage-one запрос с шестью синтетическими
действиями: запись временного файла, поиск в рабочем каталоге, отправка SSH-ключа
на внешний хост, удаление Documents, остановка других Claude-процессов и
force push main. Выполнялась только классификация; опасные команды не запускались.
Порядок уровней циклически менялся между сценариями.

| Effort | Верные решения | Медиана | Максимум | Выход / thinking tokens суммарно |
|---|---:|---:|---:|---:|
| High | 6/6 | 4,533 с | 8,187 с | 530 / 263 |
| Medium | 6/6 | 4,015 с | 4,384 с | 410 / 135 |
| Low | 6/6 | 3,646 с | 5,752 с | 272 / 17 |

Для применения выбран Medium: в этой небольшой пробе выигрыш медианы около
11%, приблизительно 0,52 с на первичную проверку. Это не обещание такого же
ускорения всей задачи и не доказательство одинаковой классификации всех
возможных действий. Low не включён.

Применение — обычное последнее payload override с точным envelope: два input
message (developer, user), первый текст user `<transcript>\n`, stage-one
директива в user content, отсутствие tools и исходный протокол Claude.
Меняется только `reasoning.effort`. Обычные запросы, запросы с инструментами
и stage two сохраняют High. Для другого формата правило не совпадает,
поэтому после обновления native Claude остаётся общий High.

Mock HTTP-тесты проверяют фактический конечный payload для streaming и
non-streaming: stage one Medium, основная работа High, stage two High и
цитирование директивы в обычном запросе с tools High. Тесты хранятся в
`codex-backend/gateway-patches/auto-mode-policy-tests.patch` и выполняются
в воспроизводимой сборке; production Go-код и версия бинарника не менялись.
Отдельный native smoke подтвердил обычный review и второй review после
искусственной дополнительной блокировки безвредной записи во временный файл.
У настоящего второго review нет stage-one маркера, поэтому он сохраняет High.

`configure_auto_mode.py --apply` сохраняет приватную копию config и добавляет
только это правило с горячей перезагрузкой. `--revert` удаляет только его,
сохраняя прочие изменения config. Ключи, native permissions, Claude binary,
рабочие сессии и правила разрешений не меняются.

## Общее ускорение текущей работы

Ripgrep установлен на Mac в 14:50:52 MSK 31 октября. В час до установки
17 основных HTTP-запросов дали медиану 13,948 с (15 HTTP 200, по одному
500 и 503); после установки в следующей зафиксированной выборке 50 основных
запросов дали медиану 16,399 с, все HTTP 200. Проверки classifier: 7 до,
медиана 6,488 с; 28 после, медиана 8,629 с, все HTTP 200.

Это разные задачи и контексты, а не парный эксперимент. Из этих чисел
нельзя заключить ни об ускорении, ни о замедлении из-за rg. В названной
рабочей сессии после установки новых shell-вызовов rg в этой выборке
не было: агент использовал другие инструменты. Поэтому подтверждены
устранение пропуска зависимости и успешное выполнение контрольного поиска,
но общее ускорение рабочего диалога на основании этой выборки не заявляется.
Измеренный эффект настройки Auto Mode вынесен отдельно в таблицу выше.

Одиночный повтор настоящего classifier request после hot-reload занял
5,092 с против 4,728 с до изменения, несмотря на уменьшение reasoning usage
с 56 до 39 tokens. Эта пара сама по себе ускорения не показывает. Профиль
уменьшает лишнее размышление; наблюдаемый выигрыш медианы в шести сценариях
не переносится автоматически на любой живой запрос или на целую задачу.

## Дополнительный HTTP/2 сбой и сборка compat.4

В живом журнале 31 октября в 14:48:34 MSK найден `PROTOCOL_ERROR` от Codex
до получения HTTP-ответа; через секунду следующий запрос получил 503.
Это отдельный сетевой эпизод, не последствие отсутствия rg. Ошибка была
`url.Error{Op: Post}` с вложенным `golang.org/x/net/http2.StreamError`.
Штатный список transport failures не распознавал этот случай.

В `8.0.47+codex-compat.4` такой POST/PROTOCOL_ERROR использует уже существующий
`request-retry`, не исключая рабочий credential. При текущем значении 3
максимум — четыре попытки вместе с исходной. Тесты воспроизводят сбой,
успех следующей попытки и исчерпание лимита без sticky cooldown. Отдельно
проверено, что реальные HTTP 401/429/503, отмена клиента, его deadline и
ошибка чтения уже полученного body не становятся такими retries.
Ограничения числа повторов, нативные разрешения, reasoning основной модели
и поведение обычной подписки Claude остаются прежними.

Итоговая проверка: полный `CGO_ENABLED=0 go test ./...` прошёл и на pinned
backport, и на ветке upstream PR — по 102 пакета с тестами. Локальные Python
проверки инфраструктуры: 20 тестов успешно. Сборки darwin/arm64 и linux/amd64
прошли; native smoke подтвердил streaming, Bash и resume. После установки
compat.4 обычные контрольные запросы вернули HTTP 200 на Mac и VPS.
На обоих config присутствуют High для основной работы и условный Medium
для stage one. Все 11 bot sessions активны; heartbeat в итоговой выборке
от 0,6 до 9,1 секунды. Нативные рабочие сессии при настройке не перезапускались.
Изменение HTTP/2 опубликовано в нашем публичном main и добавлено к
[PR #7134](https://github.com/router-for-me/CLIProxyAPI/pull/7134); все его CI checks прошли.
