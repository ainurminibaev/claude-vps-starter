# Замеры задержек Claude → Codex

Измерено 30.10.2026 на Mac с GPT-6.1-Sol, High и обычным service tier.
Это локальная диагностика с небольшой выборкой, не универсальный бенчмарк.
Сырые отчёты содержат только метаданные и хранятся приватно в
`~/.config/claude-backend/latency-report-*.json`.

## Где уходит время

С одинаковыми явно заданными инструментами, по два запроса на ячейку:

| Задача | Напрямую в Codex, всё время | Через Claude endpoint шлюза, всё время |
|---|---:|---:|
| Короткий ответ | 2,53 с | 2,41 с |
| Функция JavaScript с тестами | 17,33 с | 17,48 с |

Разницу нельзя считать чистым overhead шлюза: генерация случайна, выборка
маленькая, direct использует curl HTTP/1.1, а upstream шлюза — свой uTLS/HTTP2.
Но в этой пробе нет многосекундной постоянной задержки самого переводчика.
Отдельный CPU-замер Claude→Codex на полном сохранённом запросе 425 КБ дал
7,5–8,7 мс. Полный актуальный запрос большой сессии восстановить не удалось
из-за отсутствующих blob-записей; этот CPU-замер относится к более старому
полному snapshot, а не к текущим 250 тысячам токенов.

В рабочих логах последних 100 Claude-запросов на момент диагностики:
основная модель — медиана 18,46 с (65 запросов), классификатор Auto Mode —
9,94 с (25 запросов). Эти цифры включают внешнее ожидание/генерацию и не
разделяют очередь OpenAI, prefill и вычисления модели. В основной сессии
около 250 тысяч входных токенов, большая часть читается из prompt cache.
Часть действий требует отдельной проверки Auto Mode, добавляя ещё один
модельный запрос. Проверки разрешений не отключены и их effort не снижен.

## Автоматический image_generation

Stock CLIProxyAPI 8.0.47 автоматически добавляет native OpenAI
`image_generation` даже в обычные кодовые запросы. Это отдельный механизм,
не VPS MCP-служба `imagegen`.

В парной пробе одного и того же запроса напрямую в OpenAI, с порядком
off/on/on/off, полное время составило 13,52 / 18,02 / 13,41 / 11,19 с.
Выдача видимого кода после первого текста была примерно втрое медленнее
при наличии image tool. Число входных токенов изменялось с 66 на 362.
Это наблюдение на одной задаче и двух повторениях на условие; не обещание
такого же ускорения каждой задачи.

В конфигурациях Mac и VPS выбран штатный режим:

```yaml
multimedia:
  disable-image-generation: "passthrough"
```

Он не добавляет и не удаляет image tool на текстовых endpoints: явно
переданный клиентом инструмент сохраняется. `/v1/images/generations` и
`/v1/images/edits` остаются включёнными. Существующая MCP-служба `imagegen`
не меняется. Режим `true`, отключающий изображения полностью, не используется.

После изменения, по одному контрольному запросу: код напрямую — 8,85 с,
через Claude endpoint — 9,67 с; короткий ответ — 1,37 и 1,75 с. Эти одиночные
запуски подтверждают работу маршрутов, а не статистически значимое ускорение.
Также проверено, что без image tool backend получает его отсутствие (11
входных токенов в короткой пробе), а при явном указании получает инструмент
(307 токенов). Реальная платная генерация картинки для этой проверки не нужна.

## Как повторить

Скрипт читает OAuth и локальный ключ из приватной desktop-конфигурации,
передаёт заголовки curl через stdin, не выводит токены, тела запросов и
ответов. Он не исполняет инструменты модели, но делает обычные запросы и
расходует лимиты. Два повтора означают 12 генераций.

```sh
python3 desktop-codex-backend/latency-probe.py --matched-tools \
  --output ~/.config/claude-backend/latency-report-matched.json
python3 desktop-codex-backend/latency-probe.py --image-ab \
  --output ~/.config/claude-backend/latency-report-image-ab.json
python3 desktop-codex-backend/latency-probe.py --verify-image-tools \
  --output ~/.config/claude-backend/latency-report-image-preservation.json
```

Различай первый SSE-event, первый сгенерированный event, первый видимый текст
и завершение ответа. Служебный `response.created` не означает, что модель
уже начала выдавать текст. Переводчик commentary и сетевое zstd-сжатие —
разные механизмы; сжатие не сокращает контекст или расход токенов.
