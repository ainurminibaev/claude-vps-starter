# Временная модель Codex с возвратом на подписку Claude

Схема остаётся прежней: Telegram → официальный Telegram-плагин → Claude Code.
Только запросы к модели идут через локальный CLIProxyAPI в ChatGPT/Codex.
Claude Code, его настройки, MCP, права, история и Telegram-доступы не заменяются.

Режим выбирается отдельно у каждого пользователя. На этой установке 30.10.2026
Codex включён для всех 11 ботов из реестра. Список владельцев и ботов хранится
в `/root/projects/claude-tg-instances/registry.md`; рабочие сессии — в массиве
`SESSIONS` watchdog. Новый пользователь по умолчанию остаётся на Claude,
пока администратор явно не выдаст ему доступ и не включит режим.

## Установка из репозитория

Из корня репозитория на сервере:

```bash
sudo -H bash codex-backend/install.sh root ilshat wife
```

Аргументы — пользователи, которым нужен доступ; уже зарегистрированные клиенты
сохраняются. Подробности файлов и зависимостей — в
[`codex-backend/README.md`](../codex-backend/README.md). Прежде чем включать режим,
убедиться, что установленная копия watchdog соответствует версии из этого
репозитория и сохраняет актуальный список `SESSIONS`. На действующем сервере
перед заменой `/root/claude-tg-watchdog.sh` делать резервную копию и сравнивать
отличия; замену выполнять атомарно через временный файл и `mv`.

Установщик подготавливает службу, авторизацию и обвязку. Выбор режима и
перезапуск ботов выполняются отдельно, как описано ниже. Для root-cron:
`python3 codex-backend/configure_cron.py --apply`.

## Устройство

- `scripts/claude-bot-launch.sh` → `/usr/local/bin/claude-bot-launch`.
  Watchdog использует его для root и пользователей с маркером режима.
- `$HOME/.claude/model-backend` — файл `codex`; без него режим `claude`.
- `scripts/claude-bot-env.sh` → `/usr/local/lib/claude-bot-cron/env.sh`.
  Единое окружение для ботов и root-cron. При `codex` подставляет шлюз и модель,
  при `claude` возвращает прежнюю авторизацию из `oauth-token-env`.
- `scripts/bot-backend.sh` → `/usr/local/bin/bot-backend`: выбирает режим
  следующего запуска. Отсутствие клиентского доступа запрещает включить Codex.
- `codex-backend/codex-model-proxy.service` → `/etc/systemd/system/`.
  Использует `/root/.local/bin/cli-proxy-api`, конфигурацию
  `/root/.config/codex-model-proxy/config.yaml`, автозапуск и перезапуск при сбое.
- CLIProxyAPI `v8.0.47`, сборка `linux_amd64_no-plugin`, upstream
  `https://github.com/router-for-me/CLIProxyAPI`. SHA256 архива проверен по
  опубликованному `checksums.txt`. Это сторонний адаптер протоколов.

Шлюз слушает только `127.0.0.1:18418`, требует отдельный локальный ключ каждого
пользователя; панель управления отключена. Есть SSE keepalive и безопасные
повторы до начала ответа. Прикладной код задач не меняется.

Модель — `gpt-6.1-sol`, проверенная в каталоге авторизованного аккаунта. В CLI
сохраняется `--effort high`, в конфигурации шлюза `reasoning.effort` закреплён
на `high`. Штатное окно Codex 500 000: CLI ограничен 475 000 с резервом.
Нет искусственного суффикса `[1m]`. Сжатие выполняет сам Claude Code.

## Авторизация

`prepare.py --users <пользователи>` импортирует существующий
`/root/.codex/auth.json` в формат CLIProxyAPI. Повторный запуск не затирает
OAuth-токены, которые шлюз уже обновил. Сам OAuth находится только у root в
`/root/.config/codex-model-proxy/auths/`; пользователи получают только локальные
ключи шлюза в `$HOME/.config/codex-model-proxy/client.env`.
Каталоги закрыты `0700`, файлы `0600`, владельцы клиентских файлов соответствуют
пользователям. Настоящие ключи и конфигурация с ними не попадают в git.
Локальные клиентские ключи разделяют доступ к шлюзу, а OpenAI-подписка у этой
установки общая; отдельного аккаунта OpenAI для каждого бота не создаётся.

Исходные Claude `oauth-token-env`, `settings.json`, Telegram-токены и allowlist
сохраняются. Общий `imagegen` работает отдельно, его авторизация не меняется.
При необходимости отдельного входа сервера в Codex CLIProxyAPI поддерживает
`-codex-device-login`: общую с Mac копию OAuth не следует вручную перезаписывать
поверх более свежих токенов шлюза.

## Переключение

```bash
bot-backend root codex
bot-restart.sh root
```

Возврат на обычную подписку Claude (пользователя можно заменить на `ilshat`
или `wife`):

```bash
bot-backend root claude
bot-restart.sh root
```

Если прежняя подписка заблокирована, сначала обычным способом обновить
`oauth-token-env` через `claude setup-token`. Возврат удаляет только маркер
режима. Следующий запуск использует прежний Claude и `--model opus`.
Шлюз можно выключить, когда все пользователи вернулись на Claude:
`systemctl disable --now codex-model-proxy.service`.

## Что сохраняется при возврате

- **История до и после смены модели.** Для каждого бота используется тот же
  `--resume` UUID и каталог `$HOME/.claude/projects/<cwd-с-дефисами>/`.
  Новый пустой диалог при переключении не создаётся.
- **Память и инструкции.** `CLAUDE.md`, файлы `MEMORY.md`, каталоги memory,
  навыки и проекты остаются на сервере и продолжают читаться Claude Code.
- **Настройки и инструменты.** `settings.json`, MCP-конфигурация, права,
  Telegram-токены, allowlist, группы и темы сохраняются.
- **Cron.** Код задач, команды и расписания остаются прежними. Следующий запуск
  берёт окружение в соответствии с текущим маркером режима.

При возобновлении длинного диалога Claude Code может штатно сжать контекст;
это не удаляет файлы истории. Модели могут по-разному использовать сохранённый
контекст и формулировать ответы. Если подписка Claude всё ещё заблокирована,
одного удаления маркера недостаточно — сначала нужен действующий Claude login.

Ручной `bot-restart.sh` ограничивает watchdog через `CLAUDE_TG_ONLY_USER`:
перезапуск одного бота не проверяет и не перезапускает остальных. Codex-сессии
не получают голые `1` при старте: это настоящие запросы, а не подтверждения
уже отсутствующего диалога. ID сессий для `--resume` сохраняются.

Claude Code 2.1.310 может остановить первое действие информационным окном о
`auto-mode-classifier-billing`. Watchdog подтверждает только это известное
уведомление с активной строкой `Enter to continue · Esc to cancel`; это
сохраняет работу классификатора Auto mode и не меняет разрешения инструментов.
Запросы на чтение вне рабочих директорий и другие реальные вопросы доступа
не подтверждаются этим обработчиком. См. [диагностику молчащего бота](07-troubleshooting.md#бот-принимает-telegram-но-остановился-перед-выполнением-инструмента).

## Cron без изменения кода задач

У root уже были `SHELL=/bin/bash` и `BASH_ENV=/root/.claude/oauth-token-env`.
`configure_cron.py --apply` меняет только `BASH_ENV` на общий `env.sh` и сохраняет
исходный crontab в `/root/backups/`. Команды, расписания и файлы задач не меняются.
Существующие `claude -p`, `/usr/bin/claude --model opus -p` и их вызовы из Python
наследуют нужное окружение. Алиасы Opus/Sonnet/Haiku в режиме Codex направлены
на GPT-6.1-Sol. При удалении маркера следующий cron автоматически возвращается
на обычный Claude. Собственные cron других пользователей учитываются отдельно:
системные отправки и резервное копирование от модели не зависят.

У Рафки есть отдельный ежедневный `daily-allah-name/run.sh`, который вызывает
`/usr/bin/claude -p`. Для него применено только окружение:
`python3 codex-backend/configure_cron.py --user rafka --apply`. Команда cron и
сам `run.sh` прежние. Cron Маруси (бэкап и дайджест без вызова модели) не менялись;
у остальных пользователей своих cron нет.

## Проверки

```bash
python3 -m unittest discover -s tests
systemctl status codex-model-proxy.service
bot-backend root
```

Локальные проверки: сохранение модели/аргументов/сессии при обычном Claude,
отделение старого Anthropic-токена в режиме Codex, stdout и код завершения CLI,
ошибочный режим, неизменность команд cron и повторное применение конфигурации.
На сервере: ответ модели и полный вызов инструмента через Claude CLI,
headless-команда с неизменённым `--model opus` и новым окружением,
поллинг Telegram, успешные `reply` и отправка картинки через `imagegen`.

При переключении всех 11 инстансов 30.10.2026 проверены исходные UUID сессий,
наличие transcript-файлов, совпадение сохранённых `settings.json` и
`oauth-token-env` с резервной копией, доступ к модели по каждому клиентскому
ключу и свежий heartbeat каждого Telegram-плагина. Для root и Рафки отдельно
проверен headless-запрос с существующими аргументами через cron-окружение.

Перед headless-проверками отключать Telegram-плагин: второй poller с тем же
токеном убивает poller живого бота. Для изолированных проб используются
`--setting-sources '' --strict-mcp-config --mcp-config '{"mcpServers":{}}'`
и временный `CLAUDE_CONFIG_DIR`.

## Видимые ответы во время работы

В stock CLIProxyAPI 8.0.47 публичный Codex `commentary` передаётся как скрытый
`thinking`. Поэтому вопросы во время большой задачи могут получать ответы,
которые не видны в обычном интерфейсе Claude Code. Для Mac и VPS подготовлена
[сборка 8.0.47-itab.2](../codex-backend/gateway-patches/README.md): видимые
сообщения, сохранение phase при replay, тесты, установка и откат. Сам Claude
Code и Telegram-плагин не меняются. На VPS флаг включается в службе шлюза,
на Mac — в его LaunchAgent.

Для больших контекстов включено upstream zstd-сжатие. Оно сохраняет текст,
токены и High, но сокращает объём сетевой передачи. Старая конфигурация
сохраняется в приватном `config.before-compression.*` рядом с runtime config.
Сжатие не устраняет задержку генерации и обрывы сети; при диагностике отличай
время ответа модели, отдельные проверки Auto Mode и повторы после TLS/HTTP2 ошибок.
